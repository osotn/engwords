Dear Sir,


We tested TX Power on Fn-Link WiFi module 6222B-SRC C100005 1945T5 and obtained values that lower than expected on some channels and antennas.

Given the ETSI power limits 15 dBm (2.4G) and 15.5 dBm (5G), we expected to see: (2.4G)(CCK,OFDM,HTMCS0-7) = 15 dBm, (5G)(OFDM,HTMCS0-7) = 15.5 dBm. (Limits by rate for CCK/OFDM/HTMCS0-7 >= 16 dBm).

Tx Power were correct (14-16 dBm) only on some channels and antennas (ch:1/ant:a, ch:100/ant:b, ch:140/ant:b).
See all table of all measured Tx Power values below.

It looks like base TX indexes in eFuse are incorrected for some channel groups and antennas.
We tested two modules and got the almost the same result.
Could you help us clarify the problem, is it really wrong Tx indexes in eFuse or maybe we had defective modules or something else? Please see all Tx power debugging information below (limits, eFuse).

Hello,

From Ln-Link datasheet on Fn-Link 6222B-SRC WiFi module we see the next output power typical values:
    2.4GHz: CCK_11M = 17dBm+/-2dB; OFDM_54M = 15dBm+/-2dB; HTMCS7 = 14dBm+/-2dB
    5  GHz: OFDM_54M = 15dBm+/-2dB; HTMCS7 = 14dBm+/-2dB; VTHMCS9 = 13dBm+/-2dB
But inside of RTL8822CS/RTL8822ES driver with disabled Tx power limits there are some bigger values
(tx power by rate):
    2.4GHz: CCK_11M = 18dBm; OFDM_54M = 17dBm; HTMCS7 = 16dBm
    5  GHz: OOFDM_54M = 17dBm; HTMCS7 = 16dBm; VTHMCS9 = 14dBm

These values are differ by 1, somewhere by 2 dB.

E.g. (with disabled Tx power limits),
/$ rtwpriv wlan0 mp_start
/$ rtwpriv wlan0 mp_channel 1
/$ rtwpriv wlan0 mp_rate 54M
/$ rtwpriv wlan0 mp_bandwidth 40M=0,shortGI=0
/$ rtwpriv wlan0 mp_ant_tx a
/$ rtwpriv wlan0 mp_get_txpower 0

>>wlan0    mp_get_txpower 0: 67
>>               dBm:17

It means that for the current module sample, Tx power output with TxIdx=67 should be 17 dBm.
But our measured value is close to Fn-Link datasheet values, it is about 15 dBm (for some channels 13..15dBm).

When we enable Tx power limit, the situation is the similar,
e.g. (Tx power limit is enabled and for ch:1 equals 15dBm).
/$ rtwpriv wlan0 mp_get_txpower 0

>>wlan0    mp_get_txpower 0: 59
>>               dBm:15

But measured value is about 13dBm.






Hello,

We tested Rx sensitivity of Fn-Link 6222B-SRC module and had "strange" results for 4-6 channels.
Conduction (by cable) test shown good result, e.g. for rate MCS0 min RSSI values were -91..-92 dBm for all channels.
But radiated (by radio) test shown min RSSI (for MCS0) -72..-75 dBm for 4-6 channels and -91..-92 for other channels (including 5G band).
It takes place only when Rx antennas connected near to module (case 2 on the picture), if we use a remote antenna connected to module by long (meters) cable (case 3 on the picture) then we see min RSSI (for MCS0) -91..-92 for all channels.

We tested Rx sensitivity in Rx mode (by rtwpriv tools) and in Rx+Tx mode (by iperf3, sending 2Mbps traffic), and had the same result around 5 channel.

We measured noise level by Spectrum Analyzer around 2432MHz (5 channel) on Rx antennas and from module, but measured level was lower than -95 dBm.

Could you help us to clarify the problem?

Hi,

We have encountered the issue with losing a huge number of beacons from the current AP in STA mode in real environment (not in RF box).
For example in our office with RSSI = -38dBm (~ 2 meters between device and AP) and with default beacon_lost_counter (=7) we can see HIF_EVENT_IND_BSSLOST from WiFi firmware every 5-10 seconds. This means that there are a lot of loss of 7+ beacons in a row.
Even when we increased beacon_lost_counter to 28 (set in wfx_hif_set_bss_params(..., 28)) we could also see HIF_EVENT_IND_BSSLOST, but only every few hours.

To test this, we added packet printing and module params to disable beacon control filter in WFX driver (see 0001-printk-beacons-and-bss-lost-events.patch in the attachment).

After setting the next params before connection to AP:
  # echo 1 > /sys/module/wfx/parameters/skip_beacon_filter 
  # echo 1 > /sys/module/wfx/parameters/print_beacon_lost 
  # echo 3 > /sys/module/wfx/parameters/print_rx

We don't understand the root of this problem. It looks as WiFi chip can not "see" packets from time to time when receiving.

scan_snr():
	if (res->flags & WPA_SCAN_NOISE_INVALID) {
		res->noise = is_6ghz_freq(res->freq) ?
			DEFAULT_NOISE_FLOOR_6GHZ :
			(IS_5GHZ(res->freq) ?
			 DEFAULT_NOISE_FLOOR_5GHZ : DEFAULT_NOISE_FLOOR_2GHZ);
	}

/*
 * Noise floor values to use when we have signal strength
 * measurements, but no noise floor measurements. These values were
 * measured in an office environment with many APs.
 */
#define DEFAULT_NOISE_FLOOR_2GHZ (-89)
#define DEFAULT_NOISE_FLOOR_5GHZ (-92)
#define DEFAULT_NOISE_FLOOR_6GHZ (-92)

/*
 * Channels with a great SNR can operate at full rate. What is a great SNR?
 * This doc https://supportforums.cisco.com/docs/DOC-12954 says, "the general
 * rule of thumb is that any SNR above 20 is good." This one
 * http://www.cisco.com/en/US/tech/tk722/tk809/technologies_q_and_a_item09186a00805e9a96.shtml#qa23
 * recommends 25 as a minimum SNR for 54 Mbps data rate. The estimates used in
 * scan_est_throughput() allow even smaller SNR values for the maximum rates
 * (21 for 54 Mbps, 22 for VHT80 MCS9, 24 for HT40 and HT20 MCS7). Use 25 as a
 * somewhat conservative value here.
 */
#define GREAT_SNR 25

Implementation of modified background scan in WFX linux driver

Hi,
Background scan takes too long time (about 700ms sequentially across all channels) and during this time Tx traffic is blocked (see Picture1 and Picture2 in the attachment). It is not acceptable for streaming purposes.

We have modified background scan procedure in WFX linux driver, which scans with a pause in one second (when Tx traffic is not blocked) between channels, that allows to “spread” traffic blocking over time (see Picture3 in the attachment).  As result, the background scan almost does not blocking effect on streaming.

This is a simple implementation (see a patch in the attachment), but we understand that any change to the driver can lead to unpredictable problems, especially in "corner cases". Could you do software review

1) Disabled beacon lost events (wfx_hif_set_bss_params(..., 0)) in WFX driver;

При высоких потерях пакетов в сети необходимо настроить параметры стека TCP/IP и протокола TCP для повышения устойчивости соединения и минимизации влияния потерь. Основные параметры, которые следует изменить:

1. Параметры TCP
(a) Устойчивость к потерям и задержкам
TCP Retransmission Timeout (RTO) – уменьшить начальное значение таймаута повторной передачи (можно настроить через sysctl параметр net.ipv4.tcp_retries2).
TCP Fast Retransmit & Fast Recovery – включить ускоренные повторные передачи (net.ipv4.tcp_frto=1).
Selective Acknowledgment (SACK) – включить, если поддерживается, чтобы передавать подтверждения не только на последний успешно полученный пакет, но и на конкретные потерянные (net.ipv4.tcp_sack=1).
(b) Адаптация к перегрузке сети
TCP Congestion Control Algorithm – использовать алгоритмы, более устойчивые к высоким потерям, например, Vegas, Westwood+, BBR:

sysctl -w net.ipv4.tcp_congestion_control=bbr
Initial Congestion Window (IW) – уменьшить начальный размер окна (net.ipv4.tcp_slow_start_after_idle=0), чтобы избежать перегрузки при повторном подключении.
(c) Настройки окна передачи
TCP Window Scaling (net.ipv4.tcp_window_scaling=1) – включить масштабирование окна для поддержки больших окон в условиях высоких задержек.
TCP Maximum Segment Size (MSS) – уменьшить MSS (net.ipv4.tcp_mtu_probing=1), чтобы снизить вероятность фрагментации.
2. Параметры IP
MTU Path Discovery (PMTUD) – если высокая потеря связана с фрагментацией, стоит включить PMTUD (net.ipv4.ip_no_pmtu_disc=0).
IP TTL (Time-to-Live) – увеличить TTL, если пакеты могут теряться из-за больших задержек (net.ipv4.ip_default_ttl=128).
3. Другие системные параметры
net.core.rmem_max и net.core.wmem_max – увеличить размеры буферов приема и передачи, чтобы компенсировать потери и задержки.
net.ipv4.tcp_low_latency=1 – рекомендуется включить в средах с чувствительностью к задержкам.
Эти настройки помогут уменьшить влияние потерь и повысить устойчивость TCP-соединений.

#!/bin/sh

start_wifi() {
    log_echo "Starting WIFI"

    WIFI_SSID=hostless2
    WIFI_KEY=hostless     

    IS_UP=

    while true; do
 
      #log_echo "WIFI"

      OUTPUT=$(iot-tool-ex -I iot0 -i)
      


      if [ ! -z "`echo $OUTPUT | grep -q  'Net link status: up'`" ]; then

         log_echo "Wifi no up"
         IS_UP=

         if [ ! -z "`echo $OUTPUT | grep  'SSID:' | grep -q "$WIFI_SSID"`"]; then
            iot-tool-ex  -s $WIFI_SSID  -p $WIFI_KEY  -a 9 -e 8 -I iot0
         fi


      fi

      if [ -z "$IS_UP" ]; then
          log_echo "Wifi  up"
          IS_UP=1
      fi

      sleep 0.5

Hi,

We have encountered an issue with "hardware request JOIN (0x0b) on vif 0 returned status 1" warnings in WFX driver during connection to the AP in client environments, causing connection timeout. 

kern.info kernel: [500514.541077][  T482] wlan0: authenticate with xx:xx:xx:xx:xx:x

This happens more or less frequently during connection depending on the environment.
