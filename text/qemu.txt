The BIOS must first load the bootloader.
This is exactly 512 bytes in size.
First of all, the bootloader will always start at the memory address 0x7C00. And secondly, it references the address 0x0AA55. We will start off by referencing these.

The "org" instruction tells the computer the memory address the program starts at. It is 0x7C00 as that is the specific memory address the BIOS searches for, as stated previously.

"bits 16" tells the computer to run in 16-bit mode. This means that we will not have access to any features provided in 32 or 64 bit mode, however it also means that it is easier to program.

At the end of the program, we need to limit the size of the program, and give it a special address that the BIOS will look for when identifying the program. To do this, type at the end of the program.

When we load the bootloader, we do not want to see the BIOS output. In order to get rid of it, we must clear the screen. 

This process, called "cls", will clear the screen when called.
This is through the use of the system interrupt 0x10.
More specifically, interrupt 0x10 AL=0x03. Interrupt 0x10 is the collection of interrupts used for graphics.

Setting the AL register to 0x03 through the use of the "mov" instruction, the operation performed by the interrupt will end up clearing the screen. The use of the "pusha" instruction saves the value of all the registers, as they are overwritten in this process. At the end of the process, before returning with the "ret" instruction, we must call the "popa" instruction to restore the data saved with the "pusha" instruction.

	mov ah, 00h
	int 10h
	popa
	ret

QEMU really does run a BIOS (or UEFI firmware) when emulating a full computer system. It does not just boot the operating system; it emulates the motherboard firmware that initializes the virtual hardware before handing control to the OS bootloader.

QEMU acts as a machine emulator by creating a virtualized environment that mimics real hardware (CPU, memory, disks, network cards, etc.).

    - Firmware Initiation: When QEMU starts, the virtual CPU is powered on and starts executing code from a hardcoded memory location (0xFFFFFFF0), just like a real computer.

    - BIOS/UEFI Usage: QEMU loads a firmware file (BIOS or UEFI) into this memory to perform Power-On Self-Test (POST) and initialize devices.

    - SeaBIOS/OVMF: By default, x86 QEMU uses SeaBIOS for legacy BIOS emulation. For modern UEFI booting, QEMU uses OVMF (Open Virtual Machine Format).

    - Tiny Code Generator (TCG): QEMU uses TCG to translate instructions from the guest architecture (e.g., ARM) to the host architecture (e.g., x86) on the fly.

    - KVM Accelerator: When running on the same architecture (e.g., x86 host running x86 guest), QEMU uses KVM (Kernel-based Virtual Machine) to allow the guest code to run directly on the host CPU for near-native performance.

SeaBIOS or EDK2 (UEFI) code running inside the virtual machine. 

    - Boot Phase: The BIOS runs, initializes the virtual PCI bus, VGA card, and disk controllers.
    - Bootloader Transfer: The BIOS searches for a boot sector on the virtual drive and transfers control to the operating system bootloader (e.g., GRUB).
    - Customization: You can even use the -bios flag in QEMU to point to a specific, custom BIOS file if needed.

    ; 2 nd flags : ( granularity )1 (32 - bit default )1 (64 - bit seg )0 ( AVL )0 -> 1100 b
    dw 0xffff       ; Limit ( bits 0 -15)
    dw 0x0          ; Base ( bits 0 -15)
    db 0x0          ; Base ( bits 16 -23)
    db 10011010b    ; 1 st flags , type flags
    db 11001111b    ; 2 nd flags , Limit ( bits 16 -19)
    db 0x0          ; Base ( bits 24 -31)

gdt_data : ; the data segment descriptor
    ; Same as code segment except for the type flags :
    ; type flags : ( code )0 ( expand down )0 ( writable )1 ( accessed )0 -> 0010 b
    dw 0xffff       ; Limit ( bits 0 -15)
    dw 0x0          ; Base ( bits 0 -15)
    db 0x0          ; Base ( bits 16 -23)
    db 10010010b    ; 1 st flags , type flags
    db 11001111b    ; 2 nd flags , Limit ( bits 16 -19)
    db 0x0         ; Base ( bits 24 -31)

gdt_end :       ; The reason for putting a label at the end of the
                ; GDT is so we can have the assembler calculate 
                ; the size of the GDT for the GDT decriptor ( below )

    ; GDT descriptior
    gdt_ descript or :
        dw gdt_end - gdt_start - 1  ; Size of our GDT , always less one
        dd gdt_start                ; of the true size
                                    ; Start address of our GDT

; Define some handy constants for the GDT segment descriptor offsets , which
; are what segment registers must contain when in protected mode. For example ,
; when we set DS = 0 x10 in PM , the CPU knows that we mean it to use the
; segment described at offset 0 x10 ( i.e. 16 bytes ) in our GDT , which in our
; case is the DATA segment (0 x0 -> NULL ; 0 x08 -> CODE ; 0 x10 -> DATA )
CODE_SEG equ gdt_code - gdt_start
DATA_SEG equ gdt_data - gdt_start

Коли ви встановили пакет qemu-user-static (як ми обговорювали раніше), система автоматично зареєструвала обробник для ARM-файлів у ядрі Linux через механізм binfmt_misc.
Як це працює: Коли ви запускаєте файл, ядро бачить "магічні числа" (заголовок ELF), які вказують на архітектуру ARM.
Автоматизація: Ядро замість прямого виконання звертається до /usr/bin/qemu-arm-static і передає йому ваш файл.
Результат: Ви просто пишете ./my_arm_binary, і він працює. Вам здається, що це прямий запуск, але насправді QEMU працює «під капотом» у фоновому режимі.

> vi board/qemu/arm-vexpress/post-image.sh
#!/bin/bash
BOARD_DIR="$(dirname $0)"
GENIMAGE_CFG="${BOARD_DIR}/genimage.cfg"
GENIMAGE_TMP="${BUILD_DIR}/genimage.tmp"

# Створюємо бінарний boot.scr з нашого текстового boot.cmd
${HOST_DIR}/bin/mkimage -A arm -O linux -T script -C none -d "${BOARD_DIR}/boot.cmd" "${BINARIES_DIR}/boot.scr"

cp ${BOARD_DIR}/uEnv.txt ${BINARIES_DIR}/uEnv.txt

# Запускаємо genimage для створення sdcard.img
rm -rf "${GENIMAGE_TMP}"
genimage \
    --rootpath "${TARGET_DIR}" \
    --tmppath "${GENIMAGE_TMP}" \
    --inputpath "${BINARIES_DIR}" \
    --outputpath "${BINARIES_DIR}" \
    --config "${GENIMAGE_CFG}"

exit $?
