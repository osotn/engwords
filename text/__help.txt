       log_echo "init_wfx: RF regulatory domain is not defined in KEYS partition!"

        log_echo "init_wfx: Configuring for US regularory domain."

/**
 * @brief Dynamically changes the Wi-Fi country code at runtime by power-cycling the WHD stack.
 * 
 * @param driver_handle      Pointer to the initialized WHD driver instance object.
 * @param interface_handle   Pointer to the primary Wi-Fi interface handle.
 * @param new_country_code   The new regulatory country code enum to apply.
 * @return whd_result_t      WHD_SUCCESS on success, error code otherwise.
 */
whd_result_t switch_whd_country_code(whd_driver_t driver_handle, 
                                     whd_interface_t *interface_handle, 
                                     whd_country_code_t new_country_code)
{
    whd_result_t res;
    whd_init_config_t new_init_config;

    // Step 1: Disconnect safely if currently associated to an Access Point
    // Ignore errors here if the radio was not connected to anything
    (void)whd_wifi_leave(*interface_handle);

    // Step 2: Power down the Wi-Fi driver and internal firmware stack
    res = whd_wifi_off(driver_handle);
    if (res != WHD_SUCCESS)
    {
        // Handle stack shutdown failure (e.g., driver busy, power management lock)
        return res; 
    }

    // Step 3: Clear and reinitialize the configuration structure
    // This wipes previous runtime artifacts and prepares a clean memory block
    memset(&new_init_config, 0, sizeof(whd_init_config_t));
    
    // Step 4: Inject the new regulatory country profile enum
    new_init_config.country = new_country_code;

    // Step 5: Boot the Wi-Fi radio back up with the modified regulatory rules
    res = whd_wifi_on(driver_handle, interface_handle, &new_init_config);
    if (res != WHD_SUCCESS)
    {
        // Re-boot failed (likely due to an unsupported country code by the firmware)
        return res;
    }

    return WHD_SUCCESS;
}

To optimize a system for the Infineon CYW5591X Wi-Fi chip, the dynamic relationship between the SDIO ring buffer, TCP receive window (RcvWnd), congestion window (Cwnd), and the chosen congestion control algorithm must be perfectly synchronized. The hardware firmware enforces a rigid RcvWnd cap of 26,280 bytes due to strict on-chip SRAM memory constraints. To match this on the Linux host, configuring tcp_adv_win_scale=1 with a 52,560-byte socket buffer effectively limits the maximum available TCP transmission window to exactly half the buffer size. This manual boundary directly prevents the Linux congestion control algorithm from aggressively scaling the Cwnd past the chip's actual physical capacity. While modern algorithms like BBR can be too aggressive for small embedded buffers, using a loss-based algorithm like Cubic ensures the Cwnd smoothly hovers right at the 26,280-byte ceiling instead of causing memory overruns. Meanwhile, the on-chip SDIO Rx ring buffer should ideally be provisioned slightly larger (e.g., ~32 KB) to provide a safe processing margin and prevent hardware-level packet drops during DMA bursts. When these parameters and algorithms are aligned, the system avoids data retransmissions, eliminates the risk of the chip entering a blocking "Zero Window" state, and locks in a consistent, stable hardware-limited throughput of ~40 Mbps.

Q:
"When I set tcp_wmem = 26000 and run an iperf3 client test without the -w flag over an SDIO link with a 26 KB Rx buffer, I get much better throughput compared to the default tcp_wmem settings.However, changing tcp_limit_output_bytes = 26000 has no effect on throughput; the performance remains identical to the default value. How can this behavior be explained?"

A:
The reason changing tcp_wmem improves throughput while changing tcp_limit_output_bytes does nothing comes down to where the data is being throttled and how the Linux TCP engine scales its transfer speed.Here is the exact explanation of why this happens.

1. Why tcp_wmem = 26000 dramatically increases throughput. When you use the default tcp_wmem settings, the Linux kernel allocates a massive memory buffer (often 4MB to 16MB) for your iperf3 client.
The Overwhelm: The client aggressively blasts megabytes of data down the stack into the SDIO bus.The Bottleneck: The data immediately hits the tiny 26 KB SDIO Rx Ring Buffer on the Infineon firmware.The Penalty: Because the firmware can only handle 26 KB, it is forced to drop the extra packets. This triggers massive packet drops, causing TCP timeouts, retransmissions, and forcing the TCP congestion algorithm (like Cubic or Reno) to repeatedly slash its speeds by 50%. Your throughput plummets.When you restrict tcp_wmem = 26000:You forcefully cap the entire volume of unacknowledged data allowed to exist.The Linux client is physically incapable of sending more than ~26 KB of data before stopping to wait for an ACK from the receiver.This completely eliminates packet loss at the SDIO boundary. The transmission becomes perfectly paced, steady, and frictionless, resulting in much higher sustained throughput.

2. Why tcp_limit_output_bytes makes no differenceThe tcp_limit_output_bytes parameter belongs to a system called TSQ (TCP Small Queues). It is designed to solve a completely different problem: local latency (bufferbloat), not overall throughput.It only looks downstream: tcp_limit_output_bytes only limits how many bytes can sit in the local Linux network device driver queue (the driver level right above your SDIO bus).It does not limit the socket: Even if you set tcp_limit_output_bytes = 26000, the underlying tcp_wmem socket buffer is still allowed to hold megabytes of data.

import asyncio
import warnings
from onvif import ONVIFCamera

# Suppress local self-signed SSL certificate warnings
warnings.filterwarnings("ignore", category=UserWarning)

async def main():
    print("Connecting to camera using HTTPS over port 8443...")
    
    # 1. Initialize camera object over HTTPS
    cam = ONVIFCamera('https://192.168.1.100', 8443, 'admin', 'Admin_1234', encrypt=False)
    
    try:
        # 2. Run the connection handshake
        await cam.update_xaddrs()

        # 3. Explicitly initialize the Device Management Service to fix the AttributeError
        devicemgmt_service = await cam.create_devicemgmt_service()
        
        # Pull device metadata safely using the loaded service instance
        device_info = await devicemgmt_service.GetDeviceInformation()
        print("\n🎉 CONNECTION SUCCESSFUL! 🎉")
        print(f"Manufacturer: {device_info.Manufacturer}")
        print(f"Model:        {device_info.Model}")
        print(f"Firmware:     {device_info.FirmwareVersion}")

        # 4. Explicitly initialize the Media Service
        media_service = await cam.create_media_service()
        profiles = await media_service.GetProfiles()

        print("\n--- Available Stream Profiles ---")
        for profile in profiles:
            stream_uri = await media_service.GetStreamUri({
                'StreamSetup': {'Stream': 'RTP-Unicast', 'Transport': {'Protocol': 'RTSP'}},
                'ProfileToken': profile.token
            })
            print(f"Profile: {profile.Name} (Token: {profile.token})")
            print(f"URL:     {stream_uri.Uri}\n")
            
    except Exception as e:
        print(f"\n❌ Handshake dropped: {type(e).__name__}")
        print(f"Details: {e}")
        
    finally:
        if hasattr(cam, 'close'):
            await cam.close()

if __name__ == "__main__":
    asyncio.run(main())

/**
 * @brief Updates the port whitelist by adding new ports and removing missing ones.
 * 
 * @param[in] ports  Pointer to the array containing the target new list of ports.
 * @param[in] num    Number of ports in the input array.
 * @return 0 on success, or -1 on failure (e.g., list full or uninitialized).
 */
int sdio_arb_update_whitelist_ports(const uint16_t *ports, int num)
{
    if (g_sdio_arb_whitelist == NULL) {
        return -1;
    }

    if (num < 0 || (num > 0 && ports == NULL)) {
        return -1;
    }

    if (sdio_arb_inited) {
        sdio_arb_mutex_lock();
    }

    /* --- КРОК 1: Видаляємо старі порти, яких немає у новому списку --- */
    for (int i = 0; i < (int)g_sdio_arb_whitelist->port_count; ) 
    {
        uint16_t current_old_port = g_sdio_arb_whitelist->ports[i];
        bool keep_port = false;

        // Шукаємо, чи є цей старий порт у новому масиві
        for (int j = 0; j < num; j++) {
            if (ports[j] == current_old_port) {
                keep_port = true;
                break;
            }
        }

        if (!keep_port) {
            /* Видаляємо порт методом заміщення з кінця (як у вашій del_whitelist функції) */
            HM_INFO_MSG(("Updating: Removing missing port %d from whitelist\n", current_old_port));
            
            if (i != (int)(g_sdio_arb_whitelist->port_count - 1)) {
                g_sdio_arb_whitelist->ports[i] = 
                    g_sdio_arb_whitelist->ports[g_sdio_arb_whitelist->port_count - 1];
            }
            g_sdio_arb_whitelist->ports[g_sdio_arb_whitelist->port_count - 1] = 0;
            g_sdio_arb_whitelist->port_count -= 1;
            
            /* Важливо: індекс 'i' НЕ інкрементуємо, бо на це місце став елемент із кінця масиву,
             * і його теж треба перевірити на наступній ітерації! */
        } else {
            i++; // Порт залишається, переходимо до наступного
        }
    }

    /* --- КРОК 2: Додаємо нові порти, яких ще немає у списку --- */
    for (int i = 0; i < num; i++) 
    {
        uint16_t new_port = ports[i];
        bool already_exists = false;

        // Перевіряємо, чи цей новий порт уже є в білому списку
        for (uint16_t j = 0; j < g_sdio_arb_whitelist->port_count; j++) {
            if (g_sdio_arb_whitelist->ports[j] == new_port) {
                already_exists = true;
                break;
            }
        }

        if (!already_exists) {
            /* Перевіряємо ліміт перед додаванням */
            if (g_sdio_arb_whitelist->port_count >= WHITE_LIST_PORT_MAX) {
                PRINT_HM_ERROR(("Update failed, up to %d ports can be set. List is full.\n", WHITE_LIST_PORT_MAX));
                if (sdio_arb_inited) {
                    sdio_arb_mutex_unlock();
                }
                return -1;
            }

            /* Додаємо унікальний новий порт */
            g_sdio_arb_whitelist->ports[g_sdio_arb_whitelist->port_count++] = new_port;
            HM_INFO_MSG(("Updating: Added unique white list port %d, total count:%ld\n",
                         new_port, g_sdio_arb_whitelist->port_count));
        }
    }

    if (sdio_arb_inited) {
        sdio_arb_mutex_unlock();
    }

    return 0;
}

CYW55913: Standard Magic Packet WoWL configuration using LPA / WHD API

For our application we want to wake Host Linux on WoWL magic packet (standard, UDP, dest_port=9).
Currently, we have added a UDP dest_port 9 item into the "Pkt_Filter" array configuration within the 
cycfg_peripherals.c/ol_list. And on the CM33 side, we recvfrom() packets from UDP socket bound to port 9. 
Then ourselve check packets on Magic Packet / our MAC address and wake Host Linux.

It works, but CM33 wakes on for all WoWL UDP:dest_port=9 packets in LAN packet, even with other MAC address.
I see that there are WoWL API functions in WHD: (whd_wowl_xxx) and also in LPA (cylpa_wowlpf_ol_xxx) for WoWL.

My question are those APIs supported for CYW55913 chip?
And is there some documentation or example how to use they (in particullar how CM33 can know that wakeup from deep sleep was caused by WoWL packet - event/status)?



When a packet arrives, the CM33 wakes up, parses the payload to check for our specific MAC address, and subsequently triggers a GPIO to wake up the Linux Host.The Problem:While this solution works, it is highly inefficient for battery/power consumption. The hardware packet filter currently forces the CM33 to wake up on every single broadcast/unicast Wake-on-LAN packet present in the local network, regardless of whether the target MAC matches our device or belongs to another machine on the LAN.To drastically improve power consumption, we want to delegate the Magic Packet filtering completely to the hardware layer of the CYW55913 Wi-Fi core, allowing the CM33 to remain in Deep Sleep until a valid MAC match occurs.During code inspection, we discovered the following low-power/WoWL APIs in the LPA (Low Power Assistant) middleware (v5.8.2) and WHD stack:whd_set_wowl_cap()whd_wowl_activate()whd_set_wowl_pattern()cylpa_wowlpf_ol_xxx functionsOur Questions:Is the true hardware-level WoWL (or WoWL packet filtering offload) natively supported on the CYW55913 chip when running in a hosted / dual-network-stack topology?Is there any official documentation, application note, or code example detailing how to properly configure the WHD/LPA layer to arm the hardware for a standard Magic Packet (6x 0xFF + 16x MAC) without creating a software UDP socket on the CM33 side?Should we pass the WL_WOWL_MAGIC flag directly into whd_set_wowl_cap() to let the firmware handle the pattern generation automatically based on the STA MAC address, or do we need to explicitly inject the 102-byte frame mask using whd_set_wowl_pattern()?Once the system is woken up by a valid WoWL packet via the WL_HOST_WAKE line, how can the CM33 software query the exact wake-up reason?
