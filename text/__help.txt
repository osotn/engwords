/**
 * @brief Dynamically changes the Wi-Fi country code at runtime by power-cycling the WHD stack.
 * 
 * @param driver_handle      Pointer to the initialized WHD driver instance object.
 * @param interface_handle   Pointer to the primary Wi-Fi interface handle.
 * @param new_country_code   The new regulatory country code enum to apply.
 * @return whd_result_t      WHD_SUCCESS on success, error code otherwise.
 */
whd_result_t switch_whd_country_code(whd_driver_t driver_handle, 
                                     whd_interface_t *interface_handle, 
                                     whd_country_code_t new_country_code)
{
    whd_result_t res;
    whd_init_config_t new_init_config;

    // Step 1: Disconnect safely if currently associated to an Access Point
    // Ignore errors here if the radio was not connected to anything
    (void)whd_wifi_leave(*interface_handle);

    // Step 2: Power down the Wi-Fi driver and internal firmware stack
    res = whd_wifi_off(driver_handle);
    if (res != WHD_SUCCESS)
    {
        // Handle stack shutdown failure (e.g., driver busy, power management lock)
        return res; 
    }

    // Step 3: Clear and reinitialize the configuration structure
    // This wipes previous runtime artifacts and prepares a clean memory block
    memset(&new_init_config, 0, sizeof(whd_init_config_t));
    
    // Step 4: Inject the new regulatory country profile enum
    new_init_config.country = new_country_code;

    // Step 5: Boot the Wi-Fi radio back up with the modified regulatory rules
    res = whd_wifi_on(driver_handle, interface_handle, &new_init_config);
    if (res != WHD_SUCCESS)
    {
        // Re-boot failed (likely due to an unsupported country code by the firmware)
        return res;
    }

    return WHD_SUCCESS;
}

To optimize a system for the Infineon CYW5591X Wi-Fi chip, the dynamic relationship between the SDIO ring buffer, TCP receive window (RcvWnd), congestion window (Cwnd), and the chosen congestion control algorithm must be perfectly synchronized. The hardware firmware enforces a rigid RcvWnd cap of 26,280 bytes due to strict on-chip SRAM memory constraints. To match this on the Linux host, configuring tcp_adv_win_scale=1 with a 52,560-byte socket buffer effectively limits the maximum available TCP transmission window to exactly half the buffer size. This manual boundary directly prevents the Linux congestion control algorithm from aggressively scaling the Cwnd past the chip's actual physical capacity. While modern algorithms like BBR can be too aggressive for small embedded buffers, using a loss-based algorithm like Cubic ensures the Cwnd smoothly hovers right at the 26,280-byte ceiling instead of causing memory overruns. Meanwhile, the on-chip SDIO Rx ring buffer should ideally be provisioned slightly larger (e.g., ~32 KB) to provide a safe processing margin and prevent hardware-level packet drops during DMA bursts. When these parameters and algorithms are aligned, the system avoids data retransmissions, eliminates the risk of the chip entering a blocking "Zero Window" state, and locks in a consistent, stable hardware-limited throughput of ~40 Mbps.

Q:
"When I set tcp_wmem = 26000 and run an iperf3 client test without the -w flag over an SDIO link with a 26 KB Rx buffer, I get much better throughput compared to the default tcp_wmem settings.However, changing tcp_limit_output_bytes = 26000 has no effect on throughput; the performance remains identical to the default value. How can this behavior be explained?"

A:
The reason changing tcp_wmem improves throughput while changing tcp_limit_output_bytes does nothing comes down to where the data is being throttled and how the Linux TCP engine scales its transfer speed.Here is the exact explanation of why this happens.

1. Why tcp_wmem = 26000 dramatically increases throughput. When you use the default tcp_wmem settings, the Linux kernel allocates a massive memory buffer (often 4MB to 16MB) for your iperf3 client.
The Overwhelm: The client aggressively blasts megabytes of data down the stack into the SDIO bus.The Bottleneck: The data immediately hits the tiny 26 KB SDIO Rx Ring Buffer on the Infineon firmware.The Penalty: Because the firmware can only handle 26 KB, it is forced to drop the extra packets. This triggers massive packet drops, causing TCP timeouts, retransmissions, and forcing the TCP congestion algorithm (like Cubic or Reno) to repeatedly slash its speeds by 50%. Your throughput plummets.When you restrict tcp_wmem = 26000:You forcefully cap the entire volume of unacknowledged data allowed to exist.The Linux client is physically incapable of sending more than ~26 KB of data before stopping to wait for an ACK from the receiver.This completely eliminates packet loss at the SDIO boundary. The transmission becomes perfectly paced, steady, and frictionless, resulting in much higher sustained throughput.

2. Why tcp_limit_output_bytes makes no differenceThe tcp_limit_output_bytes parameter belongs to a system called TSQ (TCP Small Queues). It is designed to solve a completely different problem: local latency (bufferbloat), not overall throughput.It only looks downstream: tcp_limit_output_bytes only limits how many bytes can sit in the local Linux network device driver queue (the driver level right above your SDIO bus).It does not limit the socket: Even if you set tcp_limit_output_bytes = 26000, the underlying tcp_wmem socket buffer is still allowed to hold megabytes of data.
